## Why this tool exists

A spreadsheet is the most sensitive file most people own: payroll, a customer
list, a company's finances. The ordinary way to turn one into a CSV is to upload
it to a stranger's server — which for a customer list is a data-protection
incident with a friendly interface. Nothing else on this site has stakes that
high. `docs/INDUSTRY_TOOL_MAP.md` §3 has the reasoning.

It is also cheap, because **an `.xlsx` is a ZIP full of XML** and the ZIP reader
and writer shipped on 2026-09-18 with CRC verification already in them.

## The three traps, and which fixture covers each

Every one of these corrupts data silently rather than failing.

**1. Text is not in the cell.** A cell holds an *index* into
`xl/sharedStrings.xml`. Read the index as the value and every text cell becomes a
small integer.

**2. A date is just a number.** Nothing in a date cell says so. The cell points
at a style, the style points at a number format, and the format decides. Miss it
and every date becomes a five-digit number; guess it wrong in the other direction
and a column of prices becomes a column of days in 1900. Format **44 is
accounting, not a date** — there is a test for exactly that.

**3. Sheet order is not file order.** `sheet1.xml` need not be the first sheet.
The relationship file maps them. Assuming otherwise hands somebody the wrong
sheet under the right name, which is worse than an error because it looks like it
worked.

### Excel's 1900 leap-year bug

Excel believes 29 February 1900 existed. It did not. Lotus 1-2-3 had the bug in
1983, Excel copied it deliberately so the two would agree, and it has been kept
for forty years because fixing it would shift every date in every file ever
saved.

The consequence: **serials either side of the phantom day are two numbers apart
and one real day apart.** No single epoch converts both correctly. `excel-date.ts`
handles it, reports serial 60 as 28 February with a `phantomLeapDay` flag, and
also handles the **1904 system** old Mac Excel used — one workbook attribute that,
ignored, puts every date out by four years and a day.

## Fixtures — and why there are two

**This is the most important thing to understand before adding tests.**

- `sales.xlsx` — written by **openpyxl**. Covers inline strings, real dates,
  booleans including `false`, negatives, a million, 0.001, unicode, an embedded
  comma, an embedded quote, an empty row, sparse cells, and a formula.
- `shared-strings.xlsx` — built **by hand from the OOXML spec**, confirmed
  readable by openpyxl. Covers shared strings, rich-text runs, XML entities,
  sheet order that disagrees with file order, a built-in *and* a custom date
  format, accounting format, and a formula's cached text result.

**Why both.** openpyxl 3.1.5 writes `t="inlineStr"` and **never writes a shared
string table at all**. Every real-world spreadsheet checked on this machine — four
of the owner's own, examined for structure only — used shared strings and `t="s"`,
and none used inline strings. So a reader tested against openpyxl alone has its
single most important code path untested, and would fail on every file Excel
itself produces. The second fixture exists for that reason.

Regenerate `sales.xlsx`:

```python
from openpyxl import Workbook
from datetime import datetime, date
wb = Workbook(); ws = wb.active; ws.title = "Sales"
ws.append(["Region", "Units", "Price", "Signed", "Notes", "Active"])
ws.append(["North", 120, 19.99, date(2023, 3, 15), "first quarter", True])
ws.append(["South", 8, 4.5, date(1970, 1, 1), "", False])
ws.append(["East", 0, -12.25, datetime(2024, 6, 1, 14, 30), "has a, comma", True])
ws.append(["West", 1000000, 0.001, date(1900, 1, 1), 'quote " inside', None])
ws["A7"] = "=A2"; ws["B7"] = 42; ws["C7"] = "unicode: हिंदी ✓"
s2 = wb.create_sheet("Empty Sheet"); s2["A1"] = "only cell"
s3 = wb.create_sheet("Gaps"); s3["A1"] = "a"; s3["D2"] = "sparse"; s3["B5"] = 5
wb.save("sales.xlsx")
```

`shared-strings.xlsx` is generated by the script in the git history of this
branch; it is eight small XML strings in a ZIP.

## Bugs already found and fixed — do not reintroduce

1. **`>` where `>=` belonged** in the 1900 conversion, so serial 60 came back as
   1 March and every phantom date moved silently forward a day. Caught by
   checking against Python's `datetime` rather than against my own reasoning.
2. **An empty `<v>` read as text.** openpyxl writes `<f>A2</f><v></v>` — a `<v>`
   that parses and holds nothing. Treating it as text produced a cell containing
   an empty string, which looks like data, sorts like data, and is not data.
3. **A test whose name did not match what it tested.** It claimed to cover shared
   strings while running against a fixture that has none. Renamed, and the real
   coverage added.

## Not done

1. **The writer.** CSV → `.xlsx`. Needs `[Content_Types].xml`, `_rels/.rels`,
   `xl/workbook.xml`, its rels, `xl/styles.xml` and a sheet. Shared strings are
   optional for writing — inline is simpler and openpyxl proves it is accepted —
   but a date column needs a style with a date `numFmtId` or it writes as a
   number. `createZip` from `lib/tools/docx/zip.ts` does the container.
2. **No UI, no route, no catalogue rows, no e2e.**
3. **No `.xls` support** (the pre-2007 binary format). Detected by its OLE
   signature and refused by name, which is the right behaviour.
4. **Formulas are not evaluated**, only their cached results shown. A file saved
   by something that did not cache results shows empty cells, and a note says so.
5. **Not verified against a real-world file.** The structure of four was
   inspected, which is what produced the shared-strings finding, but running the
   reader over one was blocked as a personal-file read — correctly. Worth doing
   with a file the owner nominates before launch.
6. **Very large sheets are not streamed.** The whole workbook is parsed into
   memory. A 100k-row sheet will be slow and should be measured before launch.
